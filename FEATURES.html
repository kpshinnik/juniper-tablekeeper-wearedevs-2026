Juniper Tablekeeper

Juniper — сервис бронирования с браузерным интерфейсом гостя, точными повторами запросов, переносом состояния, политиками по датам и повторяющимися бронями. Управляющий может рассчитать и атомарно применить новое размещение при закрытии столика. Четыре стадии созданы по письменным требованиям и независимо проверены тремя реальными агентами BAND. Все демонстрационные данные синтетические.

Локальный запуск принятой четвёртой стадии

Нужен Docker. Из корня этого репозитория первая команда проверяет соответствие отслеживаемых файлов стадий принятому продукту. Каждая стадия собирается самостоятельно; пример запускает полный сервис стадии 4.

git diff --exit-code 25ade1c7add9a5701a511e07f79a619a3cb21b51 -- stage-1 stage-2 stage-3 stage-4
cd stage-4
docker build -t juniper-tablekeeper-stage4 .
docker run --rm --name juniper-local-25ade1c --cpus=2 --memory=2g --read-only --tmpfs /tmp:rw,noexec,nosuid,size=64m -e PORT=8080 -p 8080:8080 juniper-tablekeeper-stage4

Во втором терминале, из корня репозитория, загрузите синтетический fixture. Reset заменит все локальные данные:

curl -i -X POST http://localhost:8080/_test/reset -H 'Content-Type: application/json' --data-binary @stage-4/demo-fixture.json

Откройте http://localhost:8080/. Вход: ada@example.test / juniper-demo-2026. Fixture даёт этому синтетическому гостю права управляющего juniper-garden; один сервис поддерживает брони, политики, серии, предпросмотр/применение закрытия и изменения серий. Для изменения или отмены выберите будущую дату. Реальный ресторан, платёж и внешний сервис не подключены.

Сервис слушает 0.0.0.0, начинает с пустого состояния и использует PORT, по умолчанию 8080. Для 18087 замените параметры на -e PORT=18087 -p 18087:18087 и используйте этот адрес. Ресурсы интерфейса и IANA-пояса включены в образ; внешний интернет при работе не нужен. Само отображение порта не доказывает изоляцию: независимая проверка использовала внутреннюю сеть и отдельный контейнер-клиент. Требования: 2 CPU, 2 ГиБ, до 50 запросов одновременно, готовность за 60 секунд, обычный запрос за 5 секунд, тестовое управление за 10. Измерения ниже относятся к выполненным конечным случаям. Если имя контейнера занято, выберите уникальное; останавливайте только собственную демонстрацию.

Инструкции: стадия 1, стадия 2, стадия 3, стадия 4, последовательность демонстрации.

Интерфейс гостя и правила бронирования

На / гость выбирает ресторан, местную дату и количество гостей. /signup и /login открывают регистрацию и вход; /lookup находит собственную бронь по коду. В сетке видны понятные названия столиков, время, одиночные места и разрешённые пары. Интерфейс рассчитан на работу при ширине 375px и на настольном экране, с видимыми подписями и клавиатурным фокусом. Загрузка, пустой результат, недоступное и выбранное место, успех, отказ и неопределённый результат различаются.

Поздний ответ старого поиска не подменяет новые результаты. Если столик занял другой клиент, форма и введённые данные остаются, а доступность обновляется. Потеря ответа бронирования показывает неопределённость и сохраняет точное тело запроса и ключ. После успешного повтора интерфейс получает первоначальный код и отдельно читает актуальное размещение. Число гостей хранится десятичным текстом и передаётся числовым токеном JSON без округления и придуманного верхнего предела. Прежние регрессии точного ввода проверяют 9007199254740993 и десятичную запись 1e400.

Недоступная пара отсутствует среди вариантов конкретного слота; недоступные одиночные ячейки остаются. Объединять можно только пары из combinable, без транзитивного объединения. Бронь занимает оба столика на весь интервал, отмена освобождает оба. Создание, PATCH и групповые перемещения принимают либо table_id, либо table_ids, но не вместе. Текущий ответ всегда содержит table_ids; для одиночного столика дополнительно есть table_id. Порядок пары соответствует объявлению ресторана.

Занятость — полуоткрытый интервал UTC: окончание в 20:30 позволяет следующей брони начаться ровно в 20:30. Время вводится в IANA-поясе ресторана. Несуществующее местное время отклоняется; повторяющееся разрешается в первое вхождение. Продолжительность измеряется реальным прошедшим временем. Прошедшая дата допустима, но срок отмены и изменения проверяется относительно настоящего текущего времени. Атомарное перемещение меняет 1–8 собственных броней одного ресторана; отказ оставляет их все неизменными.

Политики, история и серии третьей стадии

manager_user_ids в fixture задаёт управляющих ресторана. Они могут публиковать полные неизменяемые политики с датой действия, но не получают доступ к чужим броням. Для местной даты начала выбирается самая поздняя подходящая дата действия, при равенстве — большая версия публикации. Обычная карточка ресторана сохраняет исходный fixture. explain=true добавляет для каждого столика независимые проверки вместимости и отсутствия пересечения; оба правила могут быть ложными. Другие значения explain отклоняются.

Публикуемая политика ограничивает шаг и продолжительность диапазоном 1–1440 минут, срок отмены — 0–10080, вместимость — 1–100 для точно всех столиков ресторана. Эти пределы не сужают допустимый исходный fixture, политику 0 или ранее принятые условия. Публикация не меняет существующие брони.

Текущая бронь содержит revision и accepted_terms. Реальное изменение гостем сначала проверяет старый принятый срок отмены, затем все итоговые поля по политике новой даты, вместе заменяет условия и время окончания, увеличивает ревизию один раз и записывает только изменившиеся поля. Изменение без разницы сохраняет условия, окончание и историю, но всё равно требует редактируемой подтверждённой брони. Необязательный expected_revision в PATCH и элементах группового перемещения отклоняет устаревшее изменение до проверки срока. Каждое событие хранит собственные итоговые условия. Отмена добавляет последнее событие; повторная отмена и повтор исходного запроса ничего не добавляют.

Создание серии принимает редактируемую подтверждённую якорную бронь, общее количество 2–12 и интервал 1–4 недели. Сам якорь, его идентификаторы, ревизия, время создания, условия и история не меняются. Каждое новое вхождение самостоятельно выбирает политику даты и проверяет DST, часы работы и занятость. Ошибка не оставляет частичной серии. Реальное отдельное изменение навсегда отмечает исключение; отмена сохраняет вхождение и его прежнюю отметку. Групповая операция увеличивает ревизию каждой затронутой серии один раз. Первоначальные даты расписания остаются прежними.

Третья стадия принимает подлинные экспорты первой и второй. Текущий вид старой брони получает новое представление без выдуманных прошлых событий; первоначальный ответ повтора остаётся в прежнем формате. История, решение по условиям и чтение серии возвращают 404 всем, кроме владельца, включая гостя без входа.

Размещение и изменение серий четвёртой стадии

Четвёртая стадия добавляет три независимо проверенные API-операции. Новые экраны не требуются: подтверждение, поиск по коду и доступность показывают текущее размещение после применения плана.

Управляющий создаёт предпросмотр закрытия столика, передавая table_id и моменты from/to с явным смещением UTC. План рассматривает все подтверждённые брони, пересекающие полуоткрытый интервал, даже сидящие за другими столиками. Каждая сохраняет идентификаторы, владельца, количество гостей, начало, конец и условия. Вместимость берётся из принятых условий конкретной брони. Весь её интервал проверяется против неподвижных броней, других назначений, прежних и нового закрытия.

Точная оптимизация минимизирует число изменённых наборов столиков, затем суммарные незанятые места, затем ранги вариантов в порядке кодов брони. Одиночные столики идут перед объявленными парами в порядке fixture. Поддерживаются шесть столиков, четыре пары и шесть рассматриваемых броней; больший вход планирования может получить 422 planning_limit. Это не предел количества гостей или исходной вместимости. Малые различия рядом с огромными числами не округляются.

Предпросмотр сохраняет план и исходный ответ без изменения занятости, истории и счётчиков. Невозможное размещение даёт 409 no_feasible_plan. Применение отклоняет изменившуюся ревизию ресторана кодом stale_plan, а уже применённый план с другим ключом — plan_already_applied. Успех фиксирует закрытие и назначения вместе. Только перенесённые брони получают одну ревизию и событие reassigned с table_ids и plan_id; условия и время неизменны. Каждая затронутая серия увеличивает версию один раз без изменения исключений. Ресторан увеличивает версию один раз даже при нуле переносов. Закрытия блокируют одиночные столики и пары в поиске, создании и изменении.

Изменение серии принимает положительную expected_revision, from_index от 0 до count−1 и local_time строго HH:MM. Оно использует исходные даты расписания и текущие столики, пропуская отменённые вхождения и исключения. Каждое реальное изменение проверяет старый срок и новую политику; ошибки вне занятости имеют приоритет по индексу вхождения, затем проверяется общая занятость. При успехе изменённые брони получают по одной ревизии, серия и ресторан — по одной за операцию; новых исключений нет. Полностью неизменный результат или пустой набор сохраняет условия и счётчики. Отказ откатывает всю операцию, а повторы возвращают неизменный исходный ответ. Сервис принимает ранние экспорты и проверяет планы, закрытия и происхождение операций до замены состояния.

Данные, повторы и хранение

Рестораны и столики создаются только fixture через reset: пользователи, часовой пояс, шаг, продолжительность, срок отмены, часы работы, столики, необязательные пары и управляющие, начальные брони. Регистрация создаёт гостя; роль управляющего задаёт fixture. Пароли хранятся солёными PBKDF2-хешами. У пользователя может быть несколько неистекающих bearer-токенов; чужие брони остаются закрыты.

Создание брони, групповые перемещения, публикация политики, создание серии, предпросмотр, применение и изменение серии требуют Idempotency-Key длиной 1–255 символов. Первый успех возвращает 201; эквивалентный повтор — 200 с первоначальным JSON-ответом даже после последующих изменений. Другое тело с уже успешно использованным ключом даёт 409. Ключ разделён по пользователю, методу и пути. Отказ оставляет его свободным. Неизвестные поля не меняют поведение, но остаются частью точной идентичности JSON. Конечные числа и глубокие контейнеры сохраняют смысл при копировании, сравнении, сериализации и повторе.

Состояние находится в памяти и теряется при перезапуске контейнера. Явные экспорт и импорт переносят аккаунты, хеши, токены, конфигурацию, идентификаторы, историю и первоначальные ответы. Импорт сначала проверяет снимок, затем полностью заменяет данные, без слияния; источник после экспорта не нужен. Снимки содержат действующие учётные данные и должны оставаться приватными тестовыми материалами. Reset очищает всё. Публичное тестовое управление требуется заданием; производственное развёртывание не заявляется.

Браузер хранит сессию в local storage, незавершённое тело и ключ — в памяти страницы. Замена состояния между запросами сохраняет вход и форму; восстановление после перезагрузки страницы не обещается. Нет фонового опроса и синхронизации вкладок. HTTP-ответ закрывает соединение, обычный клиент подключается заново. Неоднозначная разметка запроса отклоняется до выполнения операции.

Независимые проверки и границы измерений

Полный отчёт стадии 4 связывает 216 замороженных / 344 независимых / 158 официальных определений, все после явного разбора имеют PASS. Все десять продемонстрированных семейств дефектов проверены напрямую: отсутствие недоступной пары, точный ввод 401 цифры, полные подписи, потеря реально принятого ответа и текущее размещение при 375/1360px. Каноническое объединение — 718 определений. Повтор стадии, переноса, запроса или адаптера не создаёт нового определения. Это выполненное покрытие, а не доказательство всех возможных случаев или результат скрытых тестов организатора.
